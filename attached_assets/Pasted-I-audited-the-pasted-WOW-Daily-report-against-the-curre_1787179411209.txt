## What I would fix in the backend next

The priority should **not** be adding another model or another specialist. The model stack is already deep enough.

The current defect is the orchestration/lifecycle boundary:

1. Instrument the `Evaluating canonical board` operation with sub-stage timestamps and per-sport counters.
2. Persist `rows_discovered`, `scanned_sports`, `source_union_counts`, model-ready count and blocked count **before** entering `SCORING`.
3. Add a watchdog for a manifest that remains `IN_PROGRESS/SCORING` without progress-heartbeat movement.
4. If canonical-board evaluation fails or times out, force a native terminal failure state rather than leaving the run indefinitely nonterminal.
5. Ensure the run can distinguish `DISCOVERY_EMPTY`, `CANONICALIZATION_STALLED`, `SCORING_EXECUTOR_TIMEOUT`, `MODEL_SERVICE_WAIT`, and `LIFECYCLE_CALLBACK_LOST`.
6. Preserve whatever sports complete successfully instead of allowing one stalled lane to prevent all row persistence.

That is the strongest technical finding from this research. **The immediate WOW problem is no longer “the model needs more intelligence.” It is that the production Daily orchestration can enter SCORING with zero persisted rows and fail to terminalize.** Until that is fixed, adding more analytical layers risks increasing complexity without improving the reliability of the output.
