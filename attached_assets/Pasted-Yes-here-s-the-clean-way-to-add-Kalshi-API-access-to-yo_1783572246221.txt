Yes — here’s the clean way to add Kalshi API access to your Custom GPT.

## Bottom line

For **WOW v16 Clean Core**, use this architecture:

**Custom GPT Action → your Replit/FastAPI proxy → Kalshi API**

Do **not** paste your Kalshi private key into the GPT instructions, Knowledge files, or action schema. Kalshi authentication requires a private RSA key and per-request RSA-PSS signatures using `KALSHI-ACCESS-KEY`, `KALSHI-ACCESS-TIMESTAMP`, and `KALSHI-ACCESS-SIGNATURE`; each signature is generated from timestamp + HTTP method + path, excluding query parameters. ([API Documentation][1])

A Custom GPT Action can call external APIs through an OpenAPI schema, but the GPT action layer is not the right place to compute Kalshi’s dynamic RSA signatures. OpenAI Actions support API key and OAuth authentication, but Actions are mainly designed to send configured auth, not hold your RSA private key and sign each request path dynamically. ([OpenAI Help Center][2])

## Why a proxy is better than direct Kalshi API

Kalshi does have public market-data endpoints that can be called without authentication, including markets, series, events, and orderbook data from the production base URL. Their public market-data quick start shows `https://external-api.kalshi.com/trade-api/v2`, and examples for `markets?series_ticker=KXHIGHNY&status=open` and `/markets/{ticker}/orderbook`. ([API Documentation][3])

But for your model, the proxy is still the right move because it can enforce the WOW rules before the GPT ever sees the result:

```text
DRY_RUN_ONLY_NO_LIVE_TRADING_NO_MARKET_ORDERS = true
can_execute = false
block all order creation/cancel/amend endpoints
stamp source = direct_api
stamp fetched_at
reject stale orderbook > 10 minutes
reject market not open
reject empty orderbook
normalize station/event/market mapping
```

That matches your current Kalshi lane rule: no live execution from GPT, Replit, Claude, or any connected tool.

## What to build in Replit

Create a tiny API service with only read-only endpoints:

```text
GET /health
GET /kalshi/markets
GET /kalshi/orderbook/{ticker}
GET /kalshi/weather/highs/{city}
GET /kalshi/evaluate/weather/{city}
```

Do **not** expose:

```text
POST /portfolio/orders
POST /portfolio/orders/batched
DELETE /portfolio/orders/{id}
PATCH /portfolio/orders/{id}
PUT /orders/...
any create/cancel/amend/fill/trade execution route
```

Kalshi’s docs list order creation, cancellation, amendment, portfolio, fills, positions, and order-group endpoints, so your wrapper should intentionally omit or hard-block them. ([API Documentation][4])

## Custom GPT setup steps

Use ChatGPT on web, not iPhone, because GPT creation/editing is limited to the web experience; mobile apps can use GPTs but not build them. ([OpenAI Help Center][5])

1. Go to **Explore GPTs → My GPTs → Edit GPT**.
2. Open **Configure**.
3. Scroll to **Actions**.
4. Click **Create new action**.
5. Use your Replit HTTPS domain as the server.
6. Set authentication to either:

   * **None**, while testing and protected by a secret route token in your backend, or
   * **API key**, if you want the GPT action to authenticate to your proxy.
7. Paste an OpenAPI schema for your proxy.
8. Test in Preview with:
   “Fetch Kalshi orderbook for ticker X and classify with WOW freshness gates.”

OpenAI says each Action needs authentication configuration plus an OpenAPI schema, and the schema tells ChatGPT which server to call, which endpoints exist, and which parameters they accept. ([OpenAI Help Center][2])

## Minimal OpenAPI schema for your Custom GPT Action

Use this as the first version. Replace `YOUR-REPLIT-APP.replit.app` with your real Replit domain.

```yaml
openapi: 3.1.0
info:
  title: WOW Kalshi Read-Only API
  version: 1.0.0
  description: Read-only Kalshi market data proxy for WOW v16 dry-run analysis. No order placement or live trading.
servers:
  - url: https://YOUR-REPLIT-APP.replit.app

paths:
  /health:
    get:
      operationId: kalshiHealth
      summary: Check Kalshi proxy health
      description: Returns proxy status, mode, dry-run flag, and whether trading endpoints are disabled.
      x-openai-isConsequential: false
      responses:
        "200":
          description: Health response

  /kalshi/markets:
    get:
      operationId: getKalshiMarkets
      summary: Search Kalshi markets
      description: Retrieves Kalshi markets using read-only market data filters.
      x-openai-isConsequential: false
      parameters:
        - name: series_ticker
          in: query
          required: false
          schema:
            type: string
          description: Kalshi series ticker, such as KXHIGHNY or KXHIGHCHI.
        - name: status
          in: query
          required: false
          schema:
            type: string
            enum: [unopened, open, closed, settled]
          description: Market status filter. Use open for active markets.
        - name: limit
          in: query
          required: false
          schema:
            type: integer
            minimum: 1
            maximum: 100
          description: Maximum number of markets to return.
      responses:
        "200":
          description: Market search response

  /kalshi/orderbook/{ticker}:
    get:
      operationId: getKalshiOrderbook
      summary: Get Kalshi orderbook
      description: Retrieves a current read-only Kalshi orderbook and returns WOW freshness metadata.
      x-openai-isConsequential: false
      parameters:
        - name: ticker
          in: path
          required: true
          schema:
            type: string
          description: Kalshi market ticker.
        - name: depth
          in: query
          required: false
          schema:
            type: integer
            minimum: 1
            maximum: 100
          description: Orderbook depth.
      responses:
        "200":
          description: Orderbook response with fetched_at, source, and freshness status.

  /kalshi/weather/highs/{city}:
    get:
      operationId: getKalshiWeatherHighMarkets
      summary: Get Kalshi daily high weather markets
      description: Retrieves weather high markets for supported WOW station mappings.
      x-openai-isConsequential: false
      parameters:
        - name: city
          in: path
          required: true
          schema:
            type: string
            enum: [NYC, LA, MIA, CHI, AUS]
          description: Supported WOW weather city code.
      responses:
        "200":
          description: Weather market response

  /kalshi/evaluate/weather/{city}:
    get:
      operationId: evaluateKalshiWeatherCity
      summary: Evaluate Kalshi weather market
      description: Runs read-only WOW weather evaluation with market freshness gates. Never places trades.
      x-openai-isConsequential: false
      parameters:
        - name: city
          in: path
          required: true
          schema:
            type: string
            enum: [NYC, LA, MIA, CHI, AUS]
        - name: sigma_f
          in: query
          required: false
          schema:
            type: number
            default: 3.5
          description: Forecast uncertainty sigma in Fahrenheit.
      responses:
        "200":
          description: WOW dry-run evaluation response
```

OpenAI’s production notes say Actions should use HTTPS/TLS, have a 45-second round-trip timeout, and keep request/response payloads under 100,000 characters, so keep these endpoints tight and paginated. ([OpenAI Developers][6])

## Replit environment variables

Store these in Replit Secrets, not in code:

```bash
KALSHI_MODE=demo
KALSHI_BASE_URL=https://external-api.demo.kalshi.co/trade-api/v2
KALSHI_KEY_ID=your_key_id
KALSHI_PRIVATE_KEY_PEM="-----BEGIN RSA PRIVATE KEY-----..."
WOW_DRY_RUN_ONLY=true
DISABLE_ORDER_ENDPOINTS=true
```

For production market data later:

```bash
KALSHI_MODE=production
KALSHI_BASE_URL=https://external-api.kalshi.com/trade-api/v2
```

Kalshi separates demo and production credentials, and demo keys only work against demo endpoints while production keys only work against production endpoints. ([API Documentation][7])

## What your GPT instructions should say

Add this to your Custom GPT instructions:

```text
Kalshi integration rules:
- Use only the WOW Kalshi Read-Only API action.
- Never request, store, display, or ask the user to paste a Kalshi private key.
- Never place, cancel, amend, or simulate submitting a live order.
- All Kalshi outputs are dry-run only.
- can_execute must always be false.
- Treat missing, stale, closed, or empty orderbooks as KALSHI_DATA_UNOBTAINABLE or KALSHI_REJECT_BAD_RULES according to WOW v16 rules.
- For weather markets, only use verified station mappings:
  NYC → KXHIGHNY → KNYC
  LA → KXHIGHLAX → KLAX
  MIA → KXHIGHMIA → KMIA
  CHI → KXHIGHCHI → KMDW
  AUS → KXHIGHAUS → KAUS
- Miami must not map to PBI. LA must not map to BUR. Chicago must not map to KORD.
```

## Best first implementation path

Start with **read-only public market data** first: `/markets`, `/series`, `/events`, `/markets/{ticker}/orderbook`. Kalshi’s public market-data guide says no authentication headers are required for those public endpoints, which lets you validate the Custom GPT Action before adding RSA signing. ([API Documentation][3])

Then add authenticated signing inside Replit only if you need account-specific endpoints, WebSocket, portfolio, fills, positions, or higher-trust trading API access. Kalshi’s API key docs make clear the private key is shown once and must be stored securely, and every trading API request must be signed with the generated private key. ([API Documentation][1])

## My recommendation for your WOW setup

Use the Custom GPT only as the **analyst interface**. Use Replit as the **Kalshi data gateway and rule enforcer**.

That gives you:

```text
GPT = asks questions, explains output, applies WOW logic
Replit = signs requests, fetches Kalshi, blocks trading, timestamps data
Kalshi = source of market/orderbook data
```

This is the safest and cleanest setup for your current rule: **dry-run only, no live trading, no market orders.**
