Patch both systems from one canonical specification and require a version handshake. Do not maintain separate “similar” instructions in the GPT and legacy platform—that is how governance drift develops.

## Correct architecture

```mermaid
flowchart TD
    A["Canonical patch registry"] --> B["WOW GPT instructions"]
    A --> C["legacy platform gate engine"]
    B --> D["Governance handshake"]
    C --> D
    D -->|Match| E["Run prop model"]
    D -->|Mismatch| F["RUN_INVALID_GOVERNANCE_MISMATCH"]
```

The GPT handles research and orchestration. legacy platform must enforce the gates in code. Neither side can override the other.

# 1. Canonical patch

Add this verbatim to the WOW master patch registry and legacy platform:

```md
# WOW-PATCH-2026-07-15-PROP-CALIBRATION-EXPOSURE-AND-SLIP-GOVERNANCE

Status: ACTIVE
Effective: 2026-07-15
Extends: WOW v16 Clean Core and all compatible active patches
Replaces: No prior patch except where directly conflicting
can_execute: false

## PURPOSE

Prevent inflated prop probabilities, adverse PrizePicks thresholds, contradictory player distributions, duplicate exposure, unsupported promo upgrades, and fragile same-game slip construction.

## 1. GOVERNANCE HANDSHAKE

Every run must include:

- master_spec_version
- active_patch_ids
- governance_hash
- engine_code_version
- research_run_id
- as_of

GPT and legacy platform must compare governance_hash before scoring.

Mismatch returns:

RUN_INVALID_GOVERNANCE_MISMATCH

No candidate, probability, confidence, slip or approval may emit after mismatch.

## 2. SETTLEMENT-AWARE MARKET DELTA

Compare actual winning, push and losing outcomes—not raw line numbers alone.

For each platform/market output:

- win_values
- push_values
- loss_values
- exact_market_match
- threshold_delta
- push_equity_delta
- market_source
- price_timestamp

A PrizePicks line is MARKET_ADVERSE when it:

- requires a more extreme result to win;
- converts a sportsbook push into a PrizePicks loss;
- lacks affirmative sportsbook support;
- or opposes the consensus/no-vig side.

MARKET_ADVERSE returns REJECT_MARKET_ADVERSE unless a verified independent model and affirmative exact-market support clear the conflict.

Examples:

- Mabrey MORE 3.5 vs sportsbook O/U 3: both require 4 to win, but 3 changes from push to PP loss — REJECT_MARKET_ADVERSE_PUSH_LOSS.
- Iriafen LESS 10.5 vs sportsbook 11: both require 10 or fewer to win, but 11 changes from push to PP loss — REJECT_MARKET_ADVERSE_PUSH_LOSS.
- Austin LESS 8.5 vs consensus 10 — REJECT_MARKET_ADVERSE_THRESHOLD.

## 3. SOURCE CEILINGS

Source order:

1. Official status/stat source
2. Two-sided sportsbook market
3. Additional sportsbook consensus
4. Trusted projection provider
5. Prediction market
6. Operator screenshot

Prediction-market support alone cannot create High confidence, MONEY_QUALIFIED or FINAL_APPROVED.

Prediction-market-only ceiling:

MARKET_VERIFIED_HOLD / MEDIUM

Two independent sportsbook sources are required for High unless the exact market is genuinely unavailable and the approved proxy pathway passes.

## 4. COMPONENT/COMPOSITE MUTEX

Create a distribution graph for each player/event:

- points
- rebounds
- assists
- FGA
- PRA
- P+R
- P+A
- R+A
- fantasy score

Block conflicting exposure across the entire session.

Examples:

- P+R MORE plus rebounds LESS
- PRA MORE plus points LESS
- FGA MORE plus points/rebounds LESS without a modeled joint explanation

Return:

DUPLICATE_EXPOSURE_BLOCK
COMPONENT_COMPOSITE_CONFLICT
REJECT_CONTRADICTORY_ROLE_STATE

An intentional middle requires explicit joint simulation, mutually compatible winning intervals and correlation review.

## 5. OPPORTUNITY-STATE CONSISTENCY

Project team totals first:

- minutes
- possessions
- points
- rebounds
- FGA
- assists
- usage

Then allocate them across active players.

Every candidate must inherit the same player opportunity state:

- projected_minutes
- usage
- attempts
- rebound_chances
- potential_assists
- role
- game_script

If multiple player LESS selections remove opportunity, the model must identify where that opportunity moves. If allocation does not reconcile, return:

REJECT_OPPORTUNITY_SUM_MISMATCH

## 6. DUPLICATE EXPOSURE

Normalize by:

event_id + player_id + stat_family + direction

Alternate thresholds and promotional versions count as one underlying distribution.

Only one active cash entry per underlying distribution is allowed during the Prop Reliability Freeze.

Bonus entries:

- count toward model and calibration exposure;
- count toward duplicate/script risk;
- do not count as cash stake when promotional credit is confirmed.

## 7. PROMO AND DEMON RULES

Taco, Goblin, Demon, discount or boosted payout status never upgrades confidence by itself.

Required:

- normal_market_line
- promotional_line
- exact threshold advantage
- sportsbook support
- raw L10 exact-threshold results
- role/status verification
- independent projection

Demon legs require stronger evidence than standard legs.

## 8. CONFIDENCE CALIBRATION

HIGH requires:

- conservative probability lower bound >= 0.65;
- exact line and settlement identity;
- confirmed status/role;
- raw L10 values;
- sportsbook consensus;
- opportunity reconciliation;
- no unresolved conflict;
- no source ceiling.

Store:

- point_estimate
- lower_bound
- upper_bound
- probability_method
- sample_size
- Brier contribution
- log-loss contribution

If the rolling 20 HIGH props hit below 58%, automatically emit:

HIGH_CONFIDENCE_SUSPENDED_CALIBRATION_FAILURE

All affected candidates cap at MEDIUM until review.

## 9. SLIP GOVERNANCE

Extended Prop Reliability Freeze:
2026-07-15 through 2026-07-22 inclusive.

During freeze:

- Core: 1–2 legs
- Flex: maximum 3 legs
- Maximum 2 legs from one event/script
- Power: every leg must be independently A-grade
- 4–6-leg Power entries: REJECT_BAD_STRUCTURE
- Repeated underlying distributions: DUPLICATE_EXPOSURE_BLOCK
- Conflicting component/composite sides: REJECT_CONTRADICTORY_ROLE_STATE

Slip requests cannot override these limits.

## 10. FINAL RULE

Final label equals the lowest mandatory gate ceiling.

No downstream probability, promo, multiplier or user request may erase an upstream blocker.

can_execute=false
```

# 5. Custom GPT/legacy platform handshake

The workflow should be:

1. GPT calls `getGovernanceStatus`.
2. GPT verifies the patch ID and hash.
3. GPT sends the board, research evidence, session exposure and expected hash.
4. legacy platform independently applies every gate.
5. legacy platform returns its applied patch list and hash.
6. GPT compares the returned hash again.
7. Any difference stops the run.

Do not allow the GPT to manufacture a final approval locally if legacy platform returns a lower ceiling.

## Definition of done

The systems are aligned only when:

* The same patch ID and hash appear in both outputs.
* All regression tests pass.
* Yesterday’s Kiki, Austin and Mabrey selections are rejected.
* Citron can be researched but cannot be duplicated or automatically called 76–81%.
* The five-pick Power is blocked before submission.
* Every result shows `can_execute=false`.

That gives you one ruleset, two independent checks, and a fail-closed response whenever the engine and legacy platform drift apart.
