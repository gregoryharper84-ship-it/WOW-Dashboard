─────────────────────────────────────────────────
PROBLEM STATEMENT
─────────────────────────────────────────────────
Sessions returning NO PLAY are correct process outputs under WOW v16, but the current output format often collapses the run into “0 approved” without showing which candidates were close, which exact fields blocked them, and what would be required to upgrade.

This creates two problems:

1. The user gets low operational value from a correct NO PLAY run.
2. Future runs repeat the same L5/L10 reconstruction work for recurring players, increasing latency and hallucination risk.

This patch does not loosen approval thresholds. It adds a standardized Validation Queue and reusable player ledger cache so the system can preserve near-miss candidates without corrupting model-approved labels.

FAILURE TAGS:

* missing-l10-ledger
* reasoned-not-modeled
* source-ledger-provenance-fail
* output-completeness-gap
* recurring-ledger-rebuild-risk

─────────────────────────────────────────────────
RULE CHANGE
─────────────────────────────────────────────────

AFFECTED SECTIONS:

* WOW-MASTER-SPEC.md Section 29.2 — Run-Level Output
* WOW-MASTER-SPEC.md Section 9 — 6-Checkpoint Gate Output Requirements
* Gate -1 Evidence Provenance Lock
* Dashboard candidate renderer

CURRENT RULE:
Run-level output lists approved/qualified/watch/rejected candidates, but no standardized blocker field, confidence-debt field, or upgrade path is required per candidate.

NEW RULE:
Every candidate that lands in MODEL_QUALIFIED_HOLD, WATCH, DATA_CONTRACT_FAIL, MARKET_VERIFIED_HOLD, or any non-approved near-miss bucket must report:

* terminal label
* display bucket
* missing fields
* confidence debt
* active blocker tags
* upgrade path
* next verification action
* cache status

This is an output and workflow requirement layered on the existing label taxonomy. It is not a parallel approval system and does not create a new playable label.

─────────────────────────────────────────────────
VALIDATION QUEUE DEFINITION
─────────────────────────────────────────────────

Validation Queue is a display bucket, not a final model label.

A row enters the Validation Queue when:

* the candidate is directionally interesting, but
* one or more required approval fields are missing, stale, contradicted, or not yet reconstructed, and
* the row is not structurally rejected.

Validation Queue rows cannot be submitted, played, promoted, or described as model-approved.

Allowed underlying labels:

* WATCH
* MODEL_QUALIFIED_HOLD
* MARKET_VERIFIED_HOLD
* DATA_CONTRACT_FAIL
* SOURCE_CONFLICT
* imported-ledger blocker states

Disallowed underlying labels:

* FINAL_APPROVED
* MONEY_QUALIFIED
* LLP_APPROVED
* LLP_PLAYABLE
* KALSHI_PLAYABLE
* REJECT_BAD_STRUCTURE
* REJECT_NO_EDGE
* REJECT_DATA_QUALITY

If a row is truly rejected, it belongs on the Rejected Board, not the Validation Queue.

─────────────────────────────────────────────────
CONFIDENCE DEBT
─────────────────────────────────────────────────

Every non-approved candidate must carry a confidence_debt object.

Required debt fields:

{
  "ledger_debt": false,
  "median_debt": false,
  "hit_count_debt": false,
  "status_debt": false,
  "role_debt": false,
  "market_debt": false,
  "payout_debt": false,
  "failure_path_debt": false,
  "source_provenance_debt": false,
  "cache_debt": false
}

Any true value blocks approval.

A row may only move from Validation Queue to Approved Board when all confidence debt fields are false and all normal WOW gates pass.

─────────────────────────────────────────────────
UPGRADE PATH REQUIREMENT
─────────────────────────────────────────────────

Every Validation Queue row must include a plain-English upgrade_path.

Examples:

* “Needs exact L10 rows and 7/10 exact-line hits.”
* “Needs market edge ≥ 2.5% after no-vig conversion.”
* “Needs player status confirmed active with no minutes restriction.”
* “Needs final PrizePicks line timestamp within allowed freshness window.”
* “Needs role confirmation because teammate availability changes usage.”
* “Needs pitcher workload confirmation after recent throwing-arm injury.”

Upgrade paths must be specific and testable.

Bad upgrade path:

“Needs more confirmation.”

Good upgrade path:

“Needs confirmed starter status, current line timestamp, and L10 exact-line hit count ≥ 7/10.”

Cache use rule:

Before web/manual reconstruction, WOW must check whether a fresh cached ledger exists.

Cache freshness rules:

* Same-day prop evaluation: cache must be refreshed after the player’s most recent completed game.
* If a new game was played after the cache timestamp, cache is stale.
* If status/injury changed after cache timestamp, status cache is stale even if game log cache is fresh.
* Stale cache may be used for scouting only, not approval.

─────────────────────────────────────────────────
FINAL PATCH PRINCIPLE
─────────────────────────────────────────────────

NO PLAY is a valid result, but NO PLAY must still be useful.

WOW does not force picks.
WOW preserves candidates.
WOW shows blockers.
WOW shows upgrade paths.
WOW only approves rows with zero confidence debt.

Main thing: don’t let legacy platform implement this as just a pretty “watch list.” The backend must calculate confidence_debt, and the renderer must only display what the backend says.
