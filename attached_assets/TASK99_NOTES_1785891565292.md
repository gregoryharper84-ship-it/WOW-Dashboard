# Task #99 — /normalize-legs 500 (NormalizedRow treated as dict)

## Root cause (reproduced, not guessed)

`gate_engine/normalizer.py`'s `NormalizedRow` dataclass only implemented
`__getitem__`, so `row['key']` worked but nothing else dict-shaped did.
I reproduced the exact crash classes against an object with that same shape:

```
row.get("resolution_status")   → AttributeError: 'NormalizedRow' object has no attribute 'get'
{**row, "extra": 1}            → TypeError: 'NormalizedRow' object is not a mapping
"resolution_status" in row     → KeyError: 0   (!) — falls back to the legacy
                                  __getitem__-only iteration protocol, which
                                  tries row[0], row[1], ... instead of a bool check
```

Any downstream code calling `.get()`, doing `**row` unpacking, or checking
`"key" in row` — a normal thing to do to something that "looks like a dict" —
crashes. That's a one-line-away bug from the docstring's own claim ("supports
dict-style access... so downstream code that expects plain dicts... works
without conversion") — `__getitem__` alone doesn't deliver on that promise.

## The fix

Make `NormalizedRow` a real `collections.abc.Mapping` in addition to being a
dataclass. Mapping supplies `.get()`, `.keys()`, `.items()`, `.values()`,
`__contains__`, and `__eq__` automatically from three methods:
`__getitem__` (already there), plus new `__iter__` and `__len__` (both
delegate to `to_dict()`, same as `__getitem__` already did — no new state,
no behavior change to existing dict output).

This is the general, comprehensive fix — it resolves `.get()`, `**row`,
`in row`, `dict(row)`, `for k in row`, `.keys()`, `.items()`, `.values()`
all at once, regardless of which specific one is crashing at your app.py
line 3031. Attribute access (`row.player_name`) is untouched.
