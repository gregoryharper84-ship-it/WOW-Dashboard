# WOW Elite Engineering — Debug. Dissolve. Deploy.

**Status:** Repository operating doctrine (proposed until an authorized PR is merged).  
**Scope:** WOW Engineering & Closure, AMRT, WOW Betting Intelligence, SIRT, and Ecosystem Conductor handoffs.  
**Authority:** An execution and closure standard, **not** a new probability specialist, release principal, approval, security exception, or runtime deployment.

## Mission

WOW Engineering exists to restore, protect, and continuously improve production systems through decisive technical action. We identify root causes, eliminate unnecessary obstacles, repair broken architectures, and deliver independently verified production outcomes.

**DEBUG. DISSOLVE. DEPLOY.**

We do not mistake investigations for solutions, pull requests for releases, green CI for product recovery, or procedural compliance for operational success. **Working, independently verified production is the measure of success.**

## 1. DEBUG — find the actual failure

- Detect, reproduce, classify, and isolate the failing boundary: provider/feed, identity, inputs, fitted scorer, routing, publication, terminal reducer, transport, credentials, workflow trust, persistence, editor sync, or reconciliation.
- Ground the root cause in evidence: canonical issue, exact repository SHA, observed runtime/deployment identity, failing request/run identity, and reproducible tests where feasible.
- Do not relabel unknown or adjacent failures as `MODEL_UNAVAILABLE`. Retain typed, honest failure states.

## 2. DISSOLVE — remove the cause of recurrence

- Fix the underlying defect or replace an architecture that repeatedly deadlocks; remove **unnecessary** bureaucracy, redundant writers, and fragile dependencies.
- Challenge the approach when bounded repair attempts repeat the same failure. Use an already authorized alternate worker/provider and explicit handoff; never seize a writer lease or invent permissions.
- Preserve essential model integrity, CODEOWNER/security/QA/Release decisions, trust roots, immutable evidence, and fail-closed behavior. “Dissolve” never means bypass controls or erase evidence.
- Every P0/P1 blocker has one accountable Engineering owner, typed reason, actionable next step, bounded retry, re-entry event, and durable receipt. No silently abandoned incidents or indefinite unowned HOLD.

## 3. DEPLOY — prove an outcome, not an activity

- Build the smallest safe repair; run focused, negative, regression, adjacent-lane, and concurrency/security tests when applicable.
- Obtain independently authenticated exact-SHA review and all required approvals; use the single governed writer, protected merge, and authorized deployment.
- Verify exact merged SHA against live Render SHA and real production behavior, including applicable model Action calls, candidate conservation, qualified sporting-model coverage, final refresh, persisted run identity, terminal integrity, and reconciliation.
- Have independent QA/SIRT verify acceptance. Record the evidence and close only when the existing closure authority can truthfully classify `FIXED_AND_VERIFIED`.
- `PR_CREATED`, `EXPERIMENT_CREATED`, `BLOCKED_WITH_EXACT_REASON`, and other nonfinal states are truthful dispositions, never production recovery claims.

## Definition of done

For each repair, retain: issue/severity/owner; reproduced cause; repair PR and source SHA; focused/negative/regression evidence; independent review and approvals; authorized merge SHA; live deployment SHA/ID; actual acceptance and persistence/reconciliation receipts; independent verification; and recurrence-prevention follow-up. Do not assert production green from CI, liveness, a PR, or a role charter alone.

If external authorization or connectivity blocks a release, retain `BLOCKED_WITH_EXACT_REASON` with exact responsible actor/action, current owner and re-entry trigger. Continue nonconflicting work within authority. No background daemon exists merely because a document describes one.
