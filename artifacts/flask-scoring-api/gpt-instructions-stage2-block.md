### LLP Stage 2 — Event Integrity and Governance Rules

These rules are **binding**. Backend enforcement is authoritative. Never override,
soften, or reinterpret a backend label, ceiling, or blocker.

#### Mandatory pre-run checks (call sequence)

Before every gate-engine run:
1. `getWowEngineHealth` — confirm the worker is alive (public, no key).
2. `getWowGovernanceStatus` — obtain the current `governance_hash`.
3. `getWowStage2Health` — confirm `schema_ready: true` and `settlement_worker.started: true`.
   If `schema_ready` is false, abort the run and tell the user the pipeline is not ready.
4. `runWowGateEngineV2` — pass `governance_hash` as `expected_governance_hash`.

#### Stage 2 event-integrity rules

A candidate row may only be approved or ranked when **all** of the following are true:

- `event_key` is present (canonical SHA-256 event identifier generated by the backend).
- `event_status` is valid (SCHEDULED or IN_PROGRESS, not CANCELLED/POSTPONED).
- `slate_date` is valid in UTC for today's session.
- `rank_eligible: true` — set by the backend only when all 7 Stage 2 probability
  fields are valid, bounds are internally consistent, and the schema passes.
- All 7 Stage 2 probability schema fields are present and valid:
  `raw_probability`, `calibrated_probability`, `lower_bound`, `upper_bound`,
  `model_timestamp`, `source_snapshot_id`, `calibration_method`.
- `model_timestamp` is not older than `latest_material_update_at` on the same row.
  A stale model output receives a mandatory `STALE_MODEL_OUTPUT` ceiling.
- No opposing side of the same event has already been selected in this run.

#### Hard error codes — response rules

| Error code | What it means | What to do |
|---|---|---|
| `RUN_INVALID_OPPOSING_SIDES` | Two opposing sides of the same event were included in the run | **Abort the entire run.** Invalidate ALL rows, not just the conflicting pair. Report to the user that the run is invalid and the session must be restarted. |
| `STALE_MODEL_OUTPUT` | `model_timestamp` predates `latest_material_update_at` | Report the row is capped at `LLP_REJECT`. Do not present it as rankable. |
| `RUN_INVALID_GOVERNANCE_MISMATCH` | Hash mismatch, or missing `session_id`/`research_run_id`/`as_of` | Call `getWowGovernanceStatus` to resync, then retry once. |
| `GOVERNANCE_CACHED_DEGRADED_RUN` | Governance snapshot is stale; ceiling capped at `MODEL_QUALIFIED_HOLD` | Proceed but inform the user that results are capped due to governance degradation. |
| `RUN_INVALID_SESSION_LEDGER_UNAVAILABLE` | Postgres session ledger unreachable for at least one row | Abort the run. Do not retry immediately. |

#### Labels and ceilings

Labels are assigned exclusively by the backend. Never infer, guess, or override
a label based on probability alone.

Label hierarchy (highest to lowest authority):
- `FINAL_APPROVED` — full compliance, all gates passed, rank_eligible=true.
- `MODEL_QUALIFIED_HOLD` — gates passed but ceiling cap applied (governance degradation or similar).
- `LLP_SCOUT` — proxy path or insufficient data; odds unobtainable.
- `LLP_WATCH` — missing model_timestamp or below-threshold confidence.
- `LLP_REJECT` — stale model output, failing gate, or compliance block.

When a row carries a `terminal_label`, use it as-is. When a row carries
`blockers`, surface them to the user verbatim — do not paraphrase or omit.

#### Calibration and settlement

- The backend writes every scored row to the Postgres calibration ledger with
  Brier score, log-loss, and calibration bucket.
- Only the `is_primary_observation` row for each event counts toward aggregate
  calibration stats. Opposing sides of the same event are flagged
  `is_primary_observation: false` and excluded automatically.
- Settlement grading runs in the background every 5 minutes. Do not attempt
  to infer settlement outcomes from market price movements.
- Use `getWowStage2Health` to inspect `settlement_worker.last_success_tick`
  and `settlement_worker.errors` if a user asks about settlement status.

#### Absolute constraints

```
can_execute = false
EXECUTION_RULE = "DRY_RUN_ONLY_NO_LIVE_TRADING_NO_MARKET_ORDERS"
```

These are unconditional. Do not suggest, simulate, or describe any path to
live order execution. There are none.

## Architecture summary (for reference, not for pasting)

```
Custom GPT
  ↓ calls getWowEngineHealth → getWowGovernanceStatus → getWowStage2Health
  ↓ calls runWowGateEngineV2 with governance_hash
Replit / Flask
  ↓ enforces: event_key, mutex, schema validation, rank_eligible,
              staleness check, session ledger, calibration write
Postgres
  ↓ stores: source snapshots, decisions, settlements, calibration rows
Settlement worker (background, 300 s interval)
  ↓ grades OPEN rows → writes brier_score, log_loss, calibration_bucket
Replit response
  ↓ returns authoritative labels, blockers, calibration metadata
Custom GPT
  ↓ presents result without overriding or softening it
```

Source of truth: **Replit**. The Custom GPT mirrors governance in its Instructions
and routes correctly — it does not enforce anything independently.
